# Talk to POS (conversational interface)

## GitHub Issues
- **Issue:** https://github.com/satisfecho/pos/issues/344
- **344**

## Problem / goal

Explore whether guests or staff can **talk to the POS** (voice and/or chat) as a useful product feature. The issue asks if this would be exciting; there is no existing design doc for a conversational POS surface. Goal for this task: decide a small first vertical slice (who speaks, which actions), document it, and implement only that slice — or a documented spike that proves feasibility — without a broad AI platform rewrite.

## High-level instructions for coder

- Read the issue for product intent only. Summarize assumptions in the task file if the ask stays vague.
- Search `docs/`, `README.md`, and current staff/public UIs for anything that already covers voice, chat, or assistant flows. Reuse patterns (i18n, public routes, auth, tenant scoping) rather than inventing a parallel stack.
- **Scope first:** pick one audience and one job (examples only — choose one and justify): staff voice shortcuts for common floor actions; public guest chat for booking/menu questions; or a settings-gated demo assistant on tenant 1. Prefer the smallest path that a user can try end-to-end.
- Prefer a **spike + short doc** (new `docs/` note or a section in an existing plan) if architecture is unclear (STT/TTS provider, browser Web Speech API vs server, offline, PII, multi-tenant secrets). Do not hard-code API keys; use `config.env` / secrets patterns.
- If implementing: keep tenant scoping and auth consistent with adjacent endpoints; no cross-tenant reads; avoid logging full transcripts with PII.
- **Out of scope:** replacing the whole UI with chat; unbounded LLM agent that can mutate orders/payments without explicit confirmation; copying secrets from the issue (none expected); marketing “live” claims before a working demo path exists.
- Pass criteria (MVP or spike): written scope (audience + actions + non-goals); either a working demo path on local HAProxy (`http://127.0.0.1:4202`) with smoke steps, or a clear spike result that says “do not build yet” with blockers listed; docs updated; append **Testing instructions** when moving to UNTESTED.
