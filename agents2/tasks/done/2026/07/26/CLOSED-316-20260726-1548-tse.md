# Feat: TSE (German Technical Security Device)

## GitHub Issues
- **Issue:** https://github.com/satisfecho/pos/issues/316
- **316**

## Problem / goal

German law (KassenSichV / §146a AO) requires every electronic POS used for business transactions to use a certified **Technical Security Device (TSE)** and issue a compliant receipt. Satisfecho has no TSE implementation or references despite targeting the German market (`satisfecho.de`). Non-compliance is legal risk for German tenants.

Closest analog: Spain VeriFactu stub (`docs/0018-verifactu-fiscal-invoicing.md`, production path `docs/0065-verifactu-production.md`) with per-tenant `fiscal_mode` (off / test / live). TSE is a **separate legal regime** — must not be conflated with VeriFactu; Spain and Germany must coexist per tenant.

## High-level instructions for coder

- **Phase 0 first:** ADR for cloud certified TSE (e.g. Fiskaly, Epson / swissbit cloud) vs local hardware dongle; prefer cloud for multi-tenant SaaS. Document legal scope caveats (tax-advisor review) like the VeriFactu docs.
- **Phase 1 MVP (after ADR):** tenant config `fiscal_country` / `tse_mode` (off | test | live), analogous to `fiscal_mode`, without cross-wiring VeriFactu logic.
- Every sale / cancellation / refund in test/live produces a **signed TSE transaction record** stored with the order via the chosen provider API.
- Printed/issued receipts include mandatory TSE fields (serial, signature counter, timestamp, QR/signature) per KassenSichV — coordinate with print-bridge work (#317 / `docs/PRINTING.md`) and Factura (`docs/0017-billing-customers-factura.md`).
- **DSFinV-K:** stub or real export for at least one date range (audit export).
- Do **not** market or enable `tse_mode: live` as certified until provider credentials + BSI TR-03153 path are verified; UI banner / `/features` honesty until then.
- New doc `docs/00XX-tse-fiscal-compliance.md` mirroring VeriFactu structure/caveats; `CHANGELOG.md`; append **Testing instructions**. No secrets in fixtures; no invented “certified” claims.
